# 운영 Redis 장애 전환 시험 결과

2026-10-25 운영 Redis를 두 AZ의 primary/replica로 구성하고 실제 장애 전환 한 번을 확인했다.
API 서버 A/C는 재시작 없이 공유 요청 제한과 응모 평가를 다시 수행했고,
합성 차단 저널 한 개의 DB 저장과 처리 완료 표시를 확인했다.
[구성과 운영 절차](redis-ha.md)를 참고한다.

## 구성과 검증 범위

| 항목 | 실제 구성 |
| --- | --- |
| Redis | Redis OSS 7.1.0, `cache.t4g.micro` 두 대, cluster mode disabled |
| 전환 전 | `001` primary / `ap-northeast-2a`, `002` replica / `ap-northeast-2c` |
| 전환 후 | `002` primary / `ap-northeast-2c`, `001` replica / `ap-northeast-2a` |
| HA | Multi-AZ·자동 장애 전환 enabled, 그룹·노드 pending 없음 |
| 연결·보호 | 기존 메인 DNS·6379·TLS·AUTH·사설 접근·저장 암호화·snapshot 0·삭제 방지 유지 |
| 앱 | A/C 모두 백엔드 `96b24cd7d70522b3031a534317376ed155b5abe4`, 기존 컨테이너 유지·재시작 0 |
| 적용 소스 | `6c69d96f24844a411385ad969a13d0e767489847` / [구현 PR #17](https://github.com/Uplus-GETDDO/getddo-infra/pull/17) |

기존에 명시된 합성 계정과 존재하지 않는 미션·이벤트 UUID만 사용했다.
소스와 정확한 ID의 읽기 조회로 업무 저장 전 거절되는 경로를 확인했다.
실제 응모·티켓 차감·보상·알림은 만들지 않았고, 의도한 DB 변경은 합성 차단 이력 한 행이다.
프론트 접근·앱 재시작·워커 중단·RDS 쓰기 게이트·부하 시험은 수행하지 않았다.

제한 대상 POST는 총 44회이며 요청 ID도 44개로 중복이 없었다.
실측 최소 요청 시작 간격은 1.1초, 동시 요청은 한 개였다.
응답은 업무 거절 404가 30회, 제한 429가 14회였고 표본의 2xx·5xx·HTTP timeout은 없었다.
이 수치는 합성 표본의 결과이며 전체 사용자 오류율이나 항상 무중단이라는 뜻이 아니다.

## 케이스별 결과

| 케이스 | 기대 동작 | 실제 결과 |
| --- | --- | --- |
| 복제본 추가·AZ 분리 | 다른 AZ의 노드 두 대와 HA 활성 | 2a/2c 배치와 primary/replica 역할을 실제 조회. 기존 endpoint·보안·엔진·사양 유지 |
| A/C 공유 카운터 | A 3회+C 2회가 합산되고 양쪽에서 초과 거절 | 전환 전후 모두 합계 5회까지 404, 다음 A/C 요청 모두 `429 / COMMON-006`과 Retry-After. Redis 값 3→5→6→7 확인 |
| 일반 제한 TTL | 실제 1분 창이 끝나면 제한 해제 | 전환 전후 A/C 모두 같은 미션 경로가 다시 `404 / MISSION-003`으로 복귀 |
| 실제 역할 전환 | 기존 replica가 primary로 승격 | AWS 이벤트에서 `001 → 002` 승격 완료와 기존 DNS 유지 확인 |
| 전환 중 fail-open | Redis 판정 실패에도 기존 업무 검증 유지 | A에서 일반 제한기 실패 경고 한 건과 `404 / MISSION-003`, 약 331ms 응답을 함께 관측 |
| 일반 연결 복구 | 앱 재시작 없이 공유 제한 처리 재개 | C와 A의 실제 카운터 기여, 양쪽 429·TTL 해제로 확인. 같은 컨테이너·재시작 0 유지 |
| 응모 평가 전용 풀 | A/C 각각 실제 Lua 평가 수행 | 전환 전후 새 이벤트 scope에서 A 요청 뒤 count 1, C 요청 뒤 count 2와 양수 PTTL 확인. 업무는 `404 / ENTRY-004`로 거절 |
| 이력 워커 전용 풀 | 합성 저널을 DB에 한 번 저장하고 ack | 사후 응모 20회 중 한도 초과 거절 10회로 저널 한 개 생성. 같은 ID의 DB 한 행·event null·`dbPersisted=true`·pending/batch 제외·owner/lease 제거를 확인하고 재조회에서도 한 행 유지 |
| 실제 복제본 복구 | 승격 이후 replica도 정상 연결 | AWS 복구 완료 이벤트, 새 primary의 connected replica 1/online, 기존 노드의 replica link up·sync in progress 0 확인 |
| 권한·설정 정리 | 시험 권한 제거, HA 유지, 전체 계획 변경 0 | 임시 inline policy 삭제·실효 implicitDeny, 즉시 적용 false, prod/bootstrap 전체 plan 변경 0 |

워커의 DB 저장→ack는 실제 처리한 워커의 전용 풀 회복 증거다.
A/C 중 어느 워커가 해당 저널을 처리했는지는 귀속하지 못했으므로 양쪽 워커 각각의 성공으로 확대하지 않는다.
단순 backlog 0이나 경고 없음으로 Lua 평가·워커 복구를 대신 판정하지 않았다.

## 시간 기록

모두 2026-10-25 KST이며, 앱 복구 시간은 낮은 빈도의 최초 성공 표본이다.
정확한 장애 지속 시간이나 다음 장애의 복구 시간 보장이 아니다.

| 관측 | 시각 | 요청 시작부터 |
| --- | --- | --- |
| 실제 전환 요청 시작 | 20:06:51.328 | 기준 |
| AWS 시험 요청 수락 이벤트 | 20:06:53.401 | 약 2.1초 |
| 기존 replica 승격 완료 이벤트 | 20:07:11.100 | 약 19.8초 |
| C 정상 카운터 기여 첫 관측 | 20:08:41.228 | 약 109.9초 |
| A 정상 카운터 기여 첫 관측 | 20:09:23.399 | 약 152.1초 |
| A/C 초과 제한 확인 | 20:10:05.471 / 20:10:11.266 | 약 194.1 / 199.9초 |
| A/C 응모 평가 기여 확인 | 20:10:14.809 / 20:10:18.455 | 약 203.5 / 207.1초 |
| 사후 합성 저널 DB 저장·ack 관측 | 20:11:33.801 | 약 282.5초 |
| 복제본 복구 완료 이벤트 | 20:15:22.342 | 약 511.0초 |

A의 전환 구간 HTTP 요청은 404 응답이 확정됐다.
그 뒤 별도로 실행한 Python 진단 연결에서 발생한 5초 TCP timeout으로 SSM 명령이 실패했으며,
이를 앱의 HTTP timeout으로 기록하지 않는다. 같은 POST를 다시 발행하지 않았다.
또한 승격 직후 AWS 노드 상태가 available이어도 실제 replica 연결은 0이었다.
복구 완료 이벤트와 Redis INFO를 확인할 때까지 앱 기능 복구와 HA 복구를 구분했다.

## 권한과 최종 관측

첫 API 호출은 AccessDenied로 명시 거절됐고 CloudTrail에도 거절과 응답 없음이 기록됐다.
정책의 실제 ARN·단일 동작·서울·만료·실행 주체·서버 시간을 대조한 뒤,
동일한 최소 임시 정책으로 준비한 후속 호출 한 번이 수락됐다.
CloudTrail 대조 결과는 API 시도 두 번 중 거절 한 번·수락 한 번이며 실제 전환은 한 번이다.
자동 재시도와 모호한 응답의 재호출은 하지 않았다. 최초 거절 원인은 확정하지 못했다.

시험 권한은 최대 30분 입력으로 생성하고 수락된 시험 이후 즉시 삭제 절차를 진행했다.
권한 만료까지 기다리지 않았으며 최종 정책 부재와 실효 거부를 확인했다.
Redis 즉시 적용 입력은 false로 복구했고 prod/bootstrap 전체 plan의 실행 변경은 모두 0이었다.
RDS는 available/Multi-AZ/2a·2c/pending 없음, CloudFront는 Deployed와 기존 WAF 연결을 유지했다.

기능 복구 이후 3분 이상 A/C 정상 읽기·기존 컨테이너·제한 동작·1분 지표를 대조했다.
ALB HealthyHostCount의 관측 구간 최솟값은 2였다.
전환 구간에는 워커 polling 연결 경고 49건과 recovery 경고 한 건을 관측했고,
20:10:18 이후 조회한 안정 구간에서는 새 WARN/ERROR를 관측하지 않았다.
ALB 5xx 지표는 미발행 구간이 있어 이를 전체 요청의 5xx 0건으로 해석하지 않는다.

합성 차단은 20:20:56.874에 만료되도록 저장됐다.
카운터는 기존 TTL, 차단·저널은 기존 만료·워커 정리 절차를 유지하며,
저널 원본·글로벌 인덱스·DB 감사 표본을 수동 삭제하지 않았다.

## 검증 근거와 한계

- 전체 Terraform 5개 root의 fmt·validate·mock 검사 74개, Python 3.12 스크립트 검사 101개와 문서 검사가 통과했다.
  [구현 PR CI](https://github.com/Uplus-GETDDO/getddo-infra/actions/runs/40184648050), [병합 main CI](https://github.com/Uplus-GETDDO/getddo-infra/actions/runs/40185119114).
- 일반 공유 연결·응모 평가 풀·이력 워커 풀을 구분해 실제 기능으로 확인했다. 앱 코드와 Redis 연결 설정은 변경하지 않았다.
- 비동기 복제로 최근 카운터·차단 상태·DB 미반영 저널이 유실될 수 있다. 이번에는 유실량이나 전환 직전 저널의 재전달을 재현하지 않았다.
  사후 생성한 표본의 한 번 저장과 ack는 무유실 보장이 아니다.
- 기존 fail-open은 업무 검증으로 넘어가는 계약이다. Redis 장애에도 모든 업무 API가 200을 반환한다는 의미가 아니다.
