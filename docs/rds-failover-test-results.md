# 운영 DB 장애 전환 테스트 결과

2026-10-25 운영 RDS의 이중화 적용 후 실제 장애 전환을 1회 시험했다.
대기 DB로의 역할 전환, 앱 재시작 없는 연결 복구, 데이터 보존과 동일 요청의 중복 방지를 확인했다.
시험용 설정을 제거하고 서비스 개방 후 정상 동작까지 확인했다.

## 시험 목적과 구성

주 DB를 사용할 수 없을 때 다른 가용 영역의 대기 DB가 역할을 이어받고,
앱이 일시 장애를 안내한 뒤 자동으로 DB 연결을 복구하는지 확인하는 것이 목적이다.
미션 보상과 응모처럼 데이터를 저장하는 기능도 전환 후 올바르게 동작하는지 확인했다.

| 구성 | 설명 |
| --- | --- |
| 운영 DB | RDS MySQL 8.4.11, `db.t4g.micro`, gp3 20 GiB |
| 이중화 방식 | Multi-AZ DB 인스턴스. 주 DB의 변경을 다른 가용 영역의 대기 DB에 동기 복제 |
| 전환 전 DB 역할 | 주 DB: `ap-northeast-2c` / 대기 DB: `ap-northeast-2a` |
| API 서버 | A는 `ap-northeast-2a`, C는 `ap-northeast-2c`에서 실행 |
| 앱 버전 | 백엔드 v0.1.10, API 서버 두 대와 기존 백그라운드 워커 7종 유지 |

대기 DB는 평소 읽기 요청을 처리하지 않는다. 전환 시 주 DB 역할을 이어받으며,
앱은 기존 DB 접속 주소를 계속 사용한다.

## 시험 방법

1. 이중화 적용과 대기 DB 초기화를 마친 뒤 15분간 정상 상태를 관찰하고 백업을 확인했다.
2. 합성 테스트 계정으로 미션을 완료해 보상을 한 번 지급받고, 저장된 결과와 티켓 잔액을 기록했다.
3. 공개 API의 쓰기 요청을 임시 제한한 뒤 RDS 관리형 강제 전환을 한 번 실행했다.
   이 제한은 시험 중 일반 사용자 요청을 막기 위한 임시 ALB 설정이다.
4. DB를 조회하는 API를 A/C에서 15초 이상, 공개 경로에서 30초 이상 간격으로 호출했다.
   RDS 이벤트·DB 역할·오류 응답·컨테이너 상태를 함께 확인했다.
5. 검증용 응모는 공개 ALB를 거치지 않고 C 서버 내부에서 직접 호출했다. 요청 실행 시점에는
   DB가 복구되어 티켓을 한 번 사용했다. A/C에서 각각 세 번 연속 정상 조회를 확인한 뒤 공개 쓰기 제한을 해제했다.
6. 미션 완료와 응모를 각각 같은 요청 키·본문으로 다시 보내 응답, 저장 건수, 티켓 원장과 잔액을 대조했다.
7. 임시 권한을 제거하고, 서비스가 열린 상태에서 5분 이상 정상 동작을 확인했다.

같은 요청 키는 서버가 동일 작업의 재전송임을 구분하는 값이다.
시험 중 앱과 워커를 재시작하거나 별도 부하를 발생시키지는 않았다.

| 티켓 잔액·원장 일치 | 보상 전후·응모 후 잔액과 지급·사용 기록 비교 | 보상 1장 증가, 응모 1장 감소 | 잔액 4 → 5 → 4. 원장도 기존 지급 4건 + 새 지급 1건 + 사용 1건으로 일치 |
| 시험용 설정 정리 | ALB 규칙·사용자 권한·Terraform 전체 계획 확인 | 원래 요청 경로 복구, 임시 권한 제거, 잔여 설정 변경 없음 | 쓰기 제한 해제·기존 ALB 규칙 복구·임시 DB 재부팅 권한 삭제. 운영·권한 관리 계획의 실행 변경 0건 |
| 서비스 개방 후 정상 동작 | 개방 후 5분 이상 DB 조회·ALB 상태·로그 관찰 | 정상 응답 유지, 새로운 장애 징후 없음 | 5분 15초 동안 정상 동작 확인. ALB 양쪽 대상 정상, 조회한 개방 이후 로그에서 새 경고·오류 없음 |

복구 시간은 A/C에서 15초 이상, 공개 경로에서 30초 이상 간격으로 호출해 처음 정상 응답을 받은 시점이다.
시험용 외부 쓰기 제한은 4분 47초였고, 준비·연속 정상 확인 시간이 포함돼 DB 연결 장애 시간과 다르다.

## 최종 상태

- 시험 후 주 DB는 2a, 대기 DB는 2c에서 정상 동작했다. DB 접속 주소·암호화·비공개·삭제 방지·백업 설정을 유지했다.
- API 서버 두 대와 백그라운드 작업은 재시작 없이 복구됐다.
- 중복 지급·응모·차감이 없었고 저장 기록과 잔액이 일치했다.
- 쓰기 제한과 임시 권한을 제거했으며, 서비스 개방 후 관찰까지 완료했다.

## 시험 범위

다음 상황은 재현하지 않았다.

- **DB를 사용할 수 없는 순간의 쓰기 실패:** 응모 요청은 조회 실패를 관측한 뒤 보냈지만 실제 실행 시점에는 복구되어 정상 저장됐다.
- **저장 직후 응답만 유실되는 상황:** DB에는 저장됐지만 사용자가 완료 응답을 받지 못하는 경우다. 이번 재전송 시험은 정상 응답을 받은 요청에 대해 수행했다.

프론트의 재시도·요청 키 유지 동작은 시험 대상에 포함하지 않았다.
소켓 읽기 제한은 60초다. 연결 오류 유형에 따라 이번에 관측한 2초보다 응답이 오래 걸릴 수 있다.
