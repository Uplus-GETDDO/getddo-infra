# 운영 DB 장애 전환 테스트 결과

2026년 10월 25일 운영 RDS MySQL을 다른 가용 영역의 대기 DB로 실제 전환했다.
앱을 재시작하지 않고 DB 연결이 복구됐으며, 같은 요청을 다시 보내도 보상과 티켓 차감이
중복되지 않았다. 시험용 쓰기 제한과 임시 권한을 제거한 뒤 서비스 정상 동작을 확인했다.
아래 시각은 모두 한국 표준시(KST)다.

## 구성과 시험 목적

서비스 요청은 CloudFront → ALB → API 서버 두 대 → RDS MySQL로 전달된다.
API A 서버는 서울 리전의 `ap-northeast-2a`, API C 서버는 `ap-northeast-2c`에 있다.
A와 C는 서버가 위치한 가용 영역을 구분하는 이름이다.

RDS는 **Multi-AZ DB 인스턴스** 구성이다. 주 DB의 변경 사항을 다른 가용 영역의
대기 DB에 동기 복제한다. 대기 DB는 일반 읽기 요청을 처리하지 않으며,
장애 전환 시 주 DB 역할을 이어받는다. 앱은 기존 DB 접속 주소를 계속 사용한다.

| 항목 | 시험 구성 |
| --- | --- |
| DB | MySQL 8.4.11, `db.t4g.micro`, gp3 20 GiB |
| 전환 전 | 주 DB: 2c / 대기 DB: 2a |
| 전환 후 | 주 DB: 2a / 대기 DB: 2c |
| 앱 | 백엔드 v0.1.10, API 서버 두 대와 알림·추첨 등 백그라운드 워커 7종 유지 |
| 연결 설정 | 풀에서 연결 획득 2초, 연결 검증 1초, JDBC 연결 2초, 소켓 읽기 60초 |
| DNS 캐시 | 정상 조회 30초, 실패한 조회 5초 |
| 데이터 보호 | 비공개 접속·암호화·삭제 방지·자동 백업 1일 유지, 작업 전 수동 스냅샷 확보 |

확인할 사항은 다음과 같았다.

1. 대기 DB가 실제로 주 DB 역할을 이어받는가?
2. DB 연결이 끊긴 동안 앱이 일시 장애를 알리고, 재시작 없이 다시 연결하는가?
3. 전환 전 저장한 데이터가 유지되고, 같은 요청의 재전송이 중복 지급·차감을 만들지 않는가?
4. 시험용 설정을 제거한 뒤 서비스가 정상 동작하는가?

## 시험 방법

Multi-AZ 적용과 대기 DB 초기화를 마친 뒤 15분간 정상 상태를 관찰했다.
시험 직전에는 진행 중이거나 곧 실행될 업무, DB 연결 풀, 합성 테스트 계정의 기준 데이터를 확인했다.

전환 직전에 공개 API의 POST·PUT·PATCH·DELETE 요청에 임시로 503을 반환하도록 설정했다.
이 쓰기 제한은 시험 중 일반 사용자 요청을 막기 위한 조치이며, 실제 장애 시 자동으로
설정되는 기능은 아니다. 읽기 요청과 앱·워커는 유지했다.

RDS 관리형 강제 전환을 **한 번** 실행하고, DB를 조회하는 API를 A/C 서버에서
최소 15초 간격, 공개 경로에서 최소 30초 간격으로 호출했다. DB 이벤트·서버 상태·로그도 함께 확인했다.
DB 삭제, 보안 그룹 전체 차단, 앱 재시작, 부하 테스트는 수행하지 않았다.

복구 후에는 A/C에서 각각 세 번 연속 정상 조회를 확인하고 쓰기 제한을 해제했다.
기존 합성 계정의 미션 완료·응모 요청을 같은 요청 키와 본문으로 다시 보내
응답·저장 건수·티켓 원장·잔액을 비교했다. 여기서 요청 키는 같은 작업의 재전송임을
서버가 구분하는 값이다. 새 키로 다시 요청하는 경우는 이 검증에 포함하지 않는다.

| 시각 | 관측 내용 |
| --- | --- |
| 01:42:37.476 | 외부 쓰기 요청에 임시 503 적용 |
| 01:43:56.830 | RDS 강제 전환 요청 수락, 실제 호출 1회·SDK 재시도 0회 |
| 01:44:10.364 | RDS 전환 시작 이벤트 |
| 01:44:19~21 | A/C의 DB 조회 API에서 `503 / COMMON-007` 관측 |
| 01:44:34.942 | A 서버에서 첫 정상 조회 확인 |
| 01:44:49.112 | RDS 전환 완료 이벤트 |
| 01:44:49.755 | C 서버에서 첫 정상 조회 확인 |
| 01:45:05.422 | 공개 경로에서 첫 정상 조회 확인 |
| 01:45:19.799 | A/C 모두 실패 이후 세 번 연속 정상 조회 확보 |
| 01:47:24.570 | 외부 쓰기 제한 해제·기존 ALB 규칙 복구 |
| 01:49:27.893 | 시험용 DB 재부팅 권한 삭제 완료 |
| 01:52:39.934 | 서비스 개방 후 5분 이상 정상 동작 확인 |

전환 요청부터 첫 정상 조회를 확인하기까지 A는 **약 38초**, C는 **약 53초**,
공개 경로는 **약 69초**가 걸렸다. 호출 사이에 실제 복구됐을 수 있으므로
이 값은 관측된 시간이며 정확한 장애 지속 시간이나 복구 시간 보장값은 아니다.

전환 완료 직후에는 AWS 조회 API의 주/대기 가용 영역 표시가 이전 값으로 남아 있었다.
이벤트와 서비스 복구를 확인한 뒤 쓰기 제한을 해제했고, 이후 조회에서
주 DB 2a·대기 DB 2c로 역할이 바뀐 것을 확인했다. 공개 쓰기 제한은 **4분 47초**였다.
이 시간에는 전환 전 준비와 연속 정상 확인·상태 확인 시간이 포함되므로 DB 연결 장애 시간과 다르다.

## 오류 응답과 앱 복구

| 항목 | 결과 |
| --- | --- |
| DB 연결 장애 응답 | HTTP 503, 오류 코드 `COMMON-007` |
| 관측한 503 응답 시간 | 약 2초 |
| 오류 안내 | “일시적으로 요청을 처리할 수 없습니다. 잠시 후 다시 시도해 주세요.” |
| 전환 요청 이후 읽기 표본 | 총 47건: 정상 43건, 503 4건(A 1·C 2·공개 경로 1) |
| 같은 표본의 502·504·클라이언트 시간 초과 | 관측 없음 |
| 앱 복구 | A/C 모두 기존 컨테이너 유지·재시작 0회 |

위 503은 DB 조회 과정에서 앱이 반환한 응답이다. 시험용 ALB 쓰기 제한의 503과 구분했다.
표본 수는 저빈도 확인 요청의 결과이며, 전체 사용자 요청 수나 전체 오류율을 뜻하지 않는다.
전환 중에는 앱·워커의 연결 대기와 오류 로그도 발생했다.

서비스 개방 후 5분 15초 동안 A/C의 DB 조회가 정상 동작했고 ALB 대상도 모두 정상이었다.
개방 이후 최종 로그 조회 구간에서는 새 WARN/ERROR가 없었으며, 연결 풀의 사용·대기 수도
최종 확인 시 0이었다. 관찰 종료 후 시험용 요청 프로세스를 종료했다.

## 데이터와 중복 처리 검증

기존 합성 테스트 계정으로 미션 완료 보상과 응모 티켓 차감을 확인했다.
전환 전에 미션 완료 요청을 한 번 보내 티켓 1장을 지급받았고,
전환 후에는 티켓 1장을 사용하는 응모 요청을 한 번 보냈다.
복구 후 두 요청을 각각 **같은 키·같은 본문으로 한 번씩** 다시 전송했다.

| 확인 항목 | 결과 |
| --- | --- |
| 최초 미션 완료 | HTTP 201, 완료 1건·보상 지급 1건 |
| 최초 응모 | HTTP 201, 응모 1건·티켓 차감 1건 |
| 같은 키로 미션·응모 재전송 | 각각 HTTP 200, 최초 응답의 데이터와 동일 |
| 최종 저장 건수 | 미션 완료 1건·보상 1건·응모 1건·차감 1건 |
| 티켓 원장 | 기존 지급 4건 보존 + 새 지급 1건 + 사용 1건 = 6건 |
| 티켓 잔액 | 시작 4장 → 미션 보상 후 5장 → 응모 후 4장 |

저장된 식별자·지급 시각·기존 원장 기록을 대조해 중복 지급·응모·차감이 없음을 확인했다.
응모에는 기존 테스트 티켓이 사용됐다. 새로 받은 보상 티켓 자체가 사용됐다는 의미는 아니다.

## 임시 설정 정리

- 이번 시험에서 만든 ALB 규칙 2개만 삭제하고 원래 규칙 전체와 일치하는지 확인했다.
  공개 경로의 비업무용 POST·PUT·PATCH·DELETE 확인 요청에서도 임시 503이 사라졌다.
- 시험용 DB 재부팅 권한을 삭제했다. 실제 사용자 권한 조회와 시뮬레이션에서
  해당 권한이 허용되지 않는 것을 확인했다. 만료만 기다린 것이 아니다.
- 최종 RDS는 정상 상태이며 보류 중인 설정 변경이 없었다. 접속 주소·암호화·비공개·
  삭제 방지·백업 설정을 유지했다.
- 운영·권한 관리 Terraform 전체 계획에서 실행할 리소스 변경과 출력 변경은 모두 0건이었다.
  실제 전환으로 바뀐 가용 영역과 최신 복원 시점의 조회값 갱신은 설정 변경과 구분했다.

## 준비 과정에서 발생한 문제

실제 전환 이전의 첫 준비에서는 CLI 로그인 정보를 SDK가 해석하지 못해 인증 단계에서 중단됐다.
이때 RDS 전환 API는 호출되지 않았다. 쓰기 제한은 **3분 7초** 후 해제했다.
또한 ALB 규칙 삭제가 성공했는데 빈 응답을 JSON으로 해석하면서 도구가 오류를 표시했다.
실제 규칙이 삭제되고 원래 구성이 복구된 것을 별도로 확인했다.

인증 정보를 SDK에 전달하는 방식을 보완하고 실제 신원을 읽기 요청으로 확인했다.
삭제 성공의 빈 응답도 처리하도록 수정한 뒤 각각 7개·11개의 도구 회귀 검사를 통과했다.
그 후 별도 시험 구간에서 위의 실제 전환 1회를 수행했다.
두 구간의 쓰기 제한은 합계 **7분 54초**였으며, 첫 준비 실패를 실제 전환 시험으로 계산하지 않았다.
다음 시험에서는 인증과 원복 도구의 확인을 쓰기 제한 전에 끝내야 한다.

## 검증하지 못한 범위

- 응모 요청은 DB 조회 실패를 관측한 뒤 보냈지만, 실제 실행 시점에는 복구되어 성공했다.
  **정확히 DB를 사용할 수 없는 순간의 쓰기 실패**나 **저장 직후 응답만 유실되는 상황**은
  재현하지 못했다. 같은 키 재전송 성공을 이 두 상황의 실증으로 확대하지 않는다.
- 소켓 읽기 제한은 60초다. 이번 503이 약 2초에 반환됐더라도 모든 장애 요청이
  8초 안에 응답하거나 프론트의 10초 제한보다 먼저 끝난다고 보장하지 않는다.
- 프론트는 변경하지 않았다. 브라우저가 재시도 시 같은 요청 키를 유지하는지는 별도 확인 대상이다.
  503 응답만으로 저장되지 않았다고 판단해서는 안 된다.
- 이번 시험은 RDS의 관리형 강제 전환이다. 실제 가용 영역 전체 장애·네트워크 단절·
  최대 부하·장기 장애를 재현한 것은 아니다.
- Multi-AZ는 잘못된 삭제도 복제한다. 백업과 복원 절차를 대체하지 않으며,
  Redis 단일 노드의 장애 대응까지 검증한 것은 아니다.
