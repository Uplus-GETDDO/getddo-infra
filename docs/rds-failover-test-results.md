# 운영 DB 장애 전환 테스트 결과

2026-10-25 운영 RDS MySQL의 Multi-AZ 장애 전환을 1회 시험했다.
API A·C는 서로 다른 가용 영역에서 실행 중인 두 서버다.

| 테스트 케이스 | 결과 |
| --- | --- |
| 주 DB에서 대기 DB로 강제 전환 | 주 DB가 2c → 2a로 변경됐고 기존 접속 주소 유지 |
| DB 연결 장애 중 API 응답 | `503 / COMMON-007` 반환, 관측한 응답 시간 약 2초 |
| 앱의 DB 재연결 | 전환 요청 후 A 약 38초·C 약 53초·공개 경로 약 69초에 첫 정상 조회 확인 |
| 앱 재시작 없이 복구 | 두 서버 모두 기존 컨테이너 유지·재시작 0회, 백그라운드 작업도 유지 |
| 전환 전 데이터 보존 | 기존 티켓 지급 기록 4건과 전환 전 미션 완료·보상 기록 유지 |
| 같은 요청 재전송 시 중복 방지 | 미션 완료·응모를 같은 요청 키와 본문으로 각각 다시 전송. 기존 결과 반환, 보상·응모·차감은 각각 1건 유지 |
| 티켓 잔액·원장 대조 | 잔액 4 → 보상 후 5 → 응모 후 4. 원장도 기존 지급 4건 + 새 지급 1건 + 사용 1건으로 일치 |
| 시험용 설정 정리 | 외부 쓰기 제한 해제·기존 ALB 규칙 복구·임시 DB 재부팅 권한 삭제 확인 |
| 서비스 개방 후 정상 동작 | 5분 이상 관찰 동안 두 서버의 DB 조회 정상, ALB 대상 정상, 조회한 로그에서 새 경고·오류 없음 |

복구 시간은 A/C 15초·공개 경로 30초 간격의 관측값이다. 정확한 장애 지속 시간이나
다음 장애의 복구 시간 보장값은 아니다. 시험용 외부 쓰기 제한은 4분 47초였으며 DB 연결 장애 시간과 다르다.

**재현하지 못한 케이스:** DB를 사용할 수 없는 순간의 쓰기 실패, 저장 직후 응답만 유실되는 상황.
응모 요청은 DB 조회 실패를 관측한 뒤 보냈지만 실제 실행 시점에는 복구되어 성공했다.
프론트의 재시도·요청 키 유지 동작은 이번 시험에 포함하지 않았다.
