# DB 연결 수 설정과 적용

운영과 스테이징은 앱 한 개의 최대 연결 수와 DB 전체 연결 한도를 나누어 관리한다.

| 설정 | 값 | 관리 위치 |
| --- | --- | --- |
| 앱별 Hikari 최대 연결 수 | 40 | 백엔드 배포 Compose |
| 앱별 최소 유휴 연결 수 | 10 | 백엔드 배포 Compose |
| DB 전체 최대 연결 수 | 100 | 환경별 RDS DB 파라미터 그룹 |

API 두 대의 풀 상한은 합계 80개다. 남은 연결은 관리·시험 접속 등에 사용하며, DB 연결 한도를 높이는 것만으로 처리량이 보장되지는 않는다. 최소 유휴 연결은 별도로 유지해 기동 시 최대 연결 수를 모두 선점하지 않도록 한다.

## 관리하는 자원

운영은 `getddo-dev-mysql84`, 스테이징은 `getddo-staging-mysql84` 파라미터 그룹을 사용한다. MySQL 계열은 `mysql8.4`이며 `max_connections`를 명시한다. DB 접속 주소·비밀번호 버전·인스턴스 사양·공개 여부·운영 Multi-AZ와 삭제 보호는 유지한다.

앱 설정은 새 환경 파일을 생성할 때 누락되지 않도록 배포 Compose의 `environment`에 둔다. 임시 환경 생성도 같은 DB 설정 그룹을 만들며, 종료 시 DB 삭제 후 그룹을 정리한다. 정리 작업은 환경·실행 식별자 태그가 일치하는 자원만 대상으로 한다.

## 적용 순서

1. DB 정비 작업과 배포 잠금이 해제됐는지 확인한다. 스테이징은 실행 중인 부하가 없는지와 만료 예약을 확인한다.
2. 운영 자동 백업과 복원 가능 시각을 확인한다. 연결 설정만 바꾸는 이 작업에서는 수동 스냅샷 생성을 필수로 요구하지 않는다.
3. 전체 Terraform 계획에서 전용 파라미터 그룹 생성과 기존 DB의 그룹 연결만 변경되는지 확인한다. DB 교체·삭제, 비밀번호 회전과 다른 자원 변경이 있으면 중단한다.
4. 작업 중에만 즉시 적용을 선택해 파라미터 그룹을 연결한다. 기본 그룹에서 새 그룹으로 전환한 설정은 일반 재부팅 후 반영을 확인한다. 강제 장애 전환은 실행하지 않는다.
5. DB가 사용 가능한 상태로 돌아오면 `SELECT @@GLOBAL.max_connections`로 실제 값을 확인한다. 파라미터 그룹 이름만으로 적용 완료를 판단하지 않는다.
6. 앱을 한 대씩 ALB에서 제외해 기존 요청 종료를 기다린 뒤 같은 이미지로 컨테이너를 다시 생성한다. 실제 Hikari 최대·최소 지표와 정상 API를 확인하고 ALB에 재등록한 다음 다른 서버를 변경한다.
7. 두 대상의 정상 상태, DB 연결 수·CPU·여유 메모리, 보류 변경 여부를 확인한다. 즉시 적용 입력은 기본값으로 돌리고 전체 계획에 남은 실행 변경이 없는지 확인한다.
8. 운영 재부팅 임시 권한을 제거하고 작업용 잠금·임시 제한을 해제한다.

운영 DB 재부팅과 스테이징 DB의 기존 설정 그룹 연결 권한은 명시한 만료 시각 안에서 지정한 DB에만 허용한다. 일반 운영자나 실행 서비스에 상시 DB 수정 권한을 추가하지 않는다. IAM은 DB 수정 요청의 개별 필드를 제한하지 못하므로 검토한 전체 계획과 적용 후 비공개·보호 설정을 함께 확인한다.

## 복구와 확인 범위

앱 설정 변경이 실패하면 변경 전 Compose와 기존 이미지로 복구한 뒤 실제 지표·정상 응답을 확인한다. 결과를 확인하지 못한 상태에서는 다음 서버를 변경하지 않는다.

DB 설정 복귀는 이전 그룹 재연결과 재부팅이 필요한 별도 작업이다. 스냅샷 복원은 새 DB 생성과 접속 전환이 필요하므로 단순 설정 복구와 구분한다. DB 응답이 돌아오지 않거나 메모리 부족이 지속되면 앱 풀 증설을 진행하지 않고 원인과 복구 방법을 먼저 확인한다.

정상 조회·연결 수 확인은 최대 처리량 또는 특정 동시 사용자 수의 합격 판정이 아니다. 성능 시험은 호출 API·읽기/쓰기 비율·대기 시간과 성공 기준을 정한 뒤 별도로 수행한다.
