# 운영 모니터링 검증 결과

2026-10-22 운영 API 서버 두 대에 Prometheus·Grafana 모니터링을 연결했다. 실제 지표 수집, 관리 포트 접근 제한, 모니터링 서버 재부팅과 백업 복원 후 데이터 유지를 확인했다.

## 시험 목적과 구성

앱·DB 연결·호스트 상태를 확인할 수 있는지, 모니터링 서버가 재시작되어도 수집과 저장 데이터가 복구되는지 시험했다.

| 구성 | 설명 |
| --- | --- |
| 수집 대상 | API A/C의 앱 지표와 node_exporter, 모니터링 서버의 node_exporter와 Prometheus 자체 지표 |
| 모니터링 서버 | t3.medium, 암호화된 루트 EBS와 별도 30 GiB gp3 데이터 EBS |
| 대시보드 | API·JVM·Hikari·Tomcat·호스트 지표와 기존 CloudWatch 지표·로그 |
| 저장·보호 | 고정 컨테이너 이미지, 데이터 볼륨 식별자 검사, Parameter Store의 관리자 비밀번호 |
| 시험 당시 접속 | SSM 포트 전달로 Grafana 접속. 이후 HTTPS 접속 구성은 [Grafana 운영 안내](grafana-https-access.md) 참고 |
| 시험 당시 앱 | 백엔드 v0.1.6, A/C 순차 배포 |

## 시험 방법

1. 모니터링 전용 자원을 구성하고 API·DB·ALB가 교체되지 않는지 확인했다.
2. A/C 앱의 관리 포트와 node_exporter를 연결하고 전체 수집 대상 상태를 조회했다.
3. Prometheus의 실제 지표와 Grafana 데이터소스의 조회 결과를 대조했다.
4. 앱 포트에서 관리 정보가 노출되지 않는지, 외부에서 관리 포트로 직접 접근할 수 없는지 확인했다.
5. 모니터링 서버를 재부팅하고 Docker·수집기·대시보드의 자동 시작과 기존 데이터 조회를 확인했다.
6. 모니터링 서비스를 멈춘 상태에서 초기 데이터를 백업하고 체크섬을 확인했다. 빈 디렉터리에 복원한 뒤 소유권·서비스·과거 샘플을 확인했다.

당시 [앱 Build](https://github.com/Uplus-GETDDO/getddo-be/actions/runs/39775170130)와 [순차 배포](https://github.com/Uplus-GETDDO/getddo-be/actions/runs/39776787035)가 성공했고, 두 서버의 실행 소스와 ALB 정상 상태를 확인했다.

## 배포 시 확인한 DB 조건

당시 포함된 V030 마이그레이션은 기존 차단 이력 테이블이 비어 있어야 했다. 사전 조회에서 10건을 발견해 배포를 중단하고 백업한 뒤 해당 이력을 정리했다. 마이그레이션 성공 후 만료된 합성 이력 10건을 생성하고 관리자 목록·상세 조회를 확인했다. 기존 스키마의 덤프는 변경된 스키마에 그대로 복원할 수 없으므로 별도 복구 검토가 필요하다.

## 시험 범위

- 대시보드는 API 조회로 확인했다. 전체 패널의 화면 검수와 부하 시험은 진행하지 않았다.
- 백업·복원 대상은 초기의 작은 데이터다. 서비스를 멈추는 백업 방식이므로 중단 중에는 수집 공백이 생긴다.
- API 서버 장애, 데이터 디스크 강제 분리와 비밀번호 누락은 이번 실환경 시험에서 재현하지 않았다.
- 자동 외부 백업·장애 알림·모니터링 서버 이중화는 이 시험에 포함하지 않았다.
