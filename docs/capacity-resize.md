# API 서버와 DB 사양 변경

운영과 스테이징은 같은 API·DB 사양을 사용한다. 운영 DB는 다른 가용 영역에 같은 사양의 대기 DB를 유지한다.

| 대상 | 운영 | 스테이징 |
| --- | --- | --- |
| API EC2 | t3.medium 두 대, 각각 2 vCPU·4 GiB | t3.medium 두 대, 각각 2 vCPU·4 GiB |
| RDS MySQL | db.t4g.medium, 2 vCPU·4 GiB, Multi-AZ | db.t4g.medium, 2 vCPU·4 GiB, Single-AZ |
| 앱별 Hikari 풀 | 최대 40, 최소 유휴 10 | 최대 40, 최소 유휴 10 |
| DB 연결 한도 | 100 | 100 |

사양 증설은 메모리 여유를 늘린다. 특정 요청 수의 처리 능력을 보장하지 않으며, 조회 방식과 동시 요청을 정한 별도 부하 시험으로 확인한다. [DB 연결 설정](database-connections.md)은 그대로 유지한다.

## 변경 방법

1. 배포·DB 정비·부하 작업이 실행 중인지 확인하고 중단 범위를 정한다. 전체 중단을 허용하면 환경별 API 두 대를 동시에 변경할 수 있다.
2. 기존 자동 백업과 보류 변경을 확인한다. 전체 Terraform 계획에서 기존 API의 instance_type과 기존 DB의 instance_class만 바뀌는지 확인한다. 삭제·교체·비밀번호 회전이나 다른 자원 변경이 있으면 진행하지 않는다.
3. API EC2는 기존 인스턴스를 정지하고 사양을 변경한 뒤 시작한다. EBS 볼륨과 기존 앱 릴리스를 유지한다. RDS는 기존 DB의 사양을 변경하며, 작업 중에만 즉시 적용을 선택한다. 운영은 대기 DB 변경과 역할 전환이 포함될 수 있고, 스테이징은 변경 중 DB 접속이 중단된다.
4. 앱과 DB가 복구되면 아래 항목을 확인한다. 작업이 끝나면 즉시 적용 입력을 기본값으로 복구하고, 임시 권한을 제거한 뒤 전체 계획의 남은 변경이 없는지 확인한다.

기존 테이블·데이터·인덱스·Flyway 적용 이력은 유지한다. DB를 새로 만들거나 데이터를 다시 적재하지 않는다. 연결 중단 시 미완료 트랜잭션은 롤백될 수 있으며, 저장 직후 응답이 끊긴 요청은 저장 여부를 확인한 뒤 재시도한다.

## 완료 확인

| 확인 항목 | 완료 기준 |
| --- | --- |
| 실제 사양 | API 네 대가 t3.medium으로 실행되고 두 RDS가 db.t4g.medium으로 available |
| 데이터와 스키마 | 기존 DB 식별자·접속 주소 유지, 변경 전후 Flyway 성공 이력·체크섬과 선택한 데이터 보존 지표 일치 |
| 앱 연결 | 기존 앱 이미지 유지, 실제 Hikari 최대 40·최소 10, SQL로 확인한 DB 연결 한도 100 |
| 서비스 | ALB 양쪽 대상 정상, 테스트 계정으로 DB를 사용하는 조회 API 성공 |
| 설정 정리 | 임시 권한 제거, 즉시 적용 기본값 복구, 전체 Terraform 계획의 실행 변경 없음 |

OpenAPI 문서 응답이나 EC2 실행 상태만으로 DB를 사용하는 서비스가 정상이라고 판단하지 않는다. 조회 실패가 남으면 사양 변경 완료와 서비스 정상 여부를 구분해 기록한다.
